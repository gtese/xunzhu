# 01 · 需求澄清与技术决策记录

记录项目从模糊需求到确定方案的完整推演过程，包含被否掉的选项与理由，避免后续重复讨论。

## 1. 初始需求

内网搭一套后端，接入飞书，上传大体量教材 PDF 建知识库，学生拍作业照片上传后给出批改与讲解。

## 2. 澄清问答与结论

| 问题 | 结论 | 对设计的影响 |
|---|---|---|
| 是否有本地 GPU | 无 | 放弃本地推理，全部走公有云 API |
| 服务器能否出网 | 可以 | 可直接调用 DashScope、飞书开放平台 |
| 客户端形态 | 公有云飞书 H5 | 不做原生 App，不做内网自建 IM |
| 学生规模 | 十几名 | 单机 Compose 足够，无需集群与 K8s |
| 教材形态 | 单年级数理化，原生电子版 PDF，单册约 200MB | PDF 有文字层，但不是纯文本，公式密集需专门处理 |
| 组件偏好 | 用成熟开源组件，不自行造轮子 | 选 pgvector / RQ / MinIO，而非自研存储与队列 |
| 服务器 | 复用 `172.16.50.166` | 需与现有 v2txt 应用隔离 |
| 域名与端口 | `edu.v2txt.cn`，对外 `52066` | 非标准端口，需实测飞书兼容性 |
| 中间件 | 独立部署，不与现有应用冲突 | 独立网络、独立卷、独立端口、独立凭据 |
| 部署方式 | 优先 Docker | 全部容器化，Compose 编排 |
| 角色设计 | 学生 / 家长 / 管理员 | 删除老师端，家长为只读视角 |

## 3. 关键技术决策

### 3.1 模型：阿里云百炼 DashScope

无 GPU，公有云 API 是唯一现实路径。选它的理由是同一平台同时提供文本、视觉、OCR、embedding、TTS，避免多供应商对接与多套计费。代价是解析阶段受 API 限流约束。

### 3.2 向量库：PostgreSQL + pgvector，否决 Milvus

15 名学生、单年级教材的量级，chunk 规模在万级。pgvector 与业务表同库同事务，备份、迁移、权限都是一套；Milvus 需要额外维护一套分布式组件，对单机 7.7G 内存的环境是纯负担。

### 3.3 队列：Redis + RQ，否决 Celery

任务类型只有三种（解析教材、识别作业、合成语音），不需要 Celery 的路由、定时、结果后端全套。RQ 更轻，与 FastAPI 集成简单。

### 3.4 不引入 RAGFlow / Dify

需求高度定制：三档 PDF 解析分流、题目按 bbox 切分、前端确认卡、家长只读视图、掌握度画像。套框架要么改不动要么绕不过去，最终成本高于直接写 FastAPI 服务。

### 3.5 不引入 Kubernetes / Kafka

单机、单实例、十几名用户。引入编排与消息中间件只增加故障面。

### 3.6 PDF 解析：三档分流，禁止整册盲跑 VLM

200MB 单册整册送 VLM，成本与耗时会失控。按页判定：有正常文字层走 PyMuPDF 直抽（L1），含图片块或特殊字体的区域裁切后送 `qwen-vl-max` 转 LaTeX（L2），文字层不可用的整页降级 `qwen-vl-ocr`（L3）。单册首轮解析成本控制在 10 元以内。

### 3.7 作业识别：强制前端确认环节

手写体识别一旦认错，后续整套讲解全部跑偏且用户无从判断。识别结果先回显给用户确认/修正，确认成本约 3 秒，换取链路准确性。这是不可省略的产品约束，不是可选优化。

### 3.8 切分：章节感知 + 公式完整性校验

固定 token 切分会把一道例题切成两半。优先用 PDF 书签建层级，无书签时用字号聚类 + 编号正则识别标题；`$$` 配对不完整的块向后合并，不允许切断公式。

### 3.9 TTS：LaTeX 先转口语再合成

`x^2` 直接送 TTS 会念成乱码。中间插一道「LaTeX → 中文口语」转换（`F = ma` → 「F 等于 m 乘以 a」），再送 CosyVoice 合成。

### 3.10 角色调整：老师端改为家长端

v1.0 设想过老师端管理后台，讨论后确认实际使用者是家长。家长端定位为**只读视角 + 可触发生成**，不能代替孩子提交作业。
